PART 01

五条知识主线 知识点不是散点，是五条互相咬合的链

  • 环境与隔离venv（PATH 前插）→ uv venv / uv sync（锁定）→ src layout → Docker 容器（未来） —— 隔离强度逐级递进：包隔离 → 项目隔离 → 系统级隔离。共同目标：任何机器上一条命令复现完全一致的环境。
  • 代码资产流git 三区 → GitHub 远端 → rebase 修分叉 → git mv / --follow 追族谱 → PR 与 CI（本周接入） —— 代码的保存、同步、追溯、协作全靠这条链；提交历史即项目履历。
  • 质量防线类型注解 + mypy（静态）→ pytest 四武器（动态）→ 约束矩阵 + 覆盖率（度量）→ pre-commit / CI（自动化，本周） —— 错误前移的四道关卡：写错时抓 → 跑时抓 → 度量盲区 → 提交前全量拦截。
  • 边界与观测pydantic 安检门 → model_validate（外部 dict）→ pydantic-settings + .env（配置边界）→ logging 结构化日志（观测边界）→ request_id 链路（下周） —— 全部在处理同一个问题：**不可信的外部世界如何安全地进入你的系统，且出了事能查到线索**。
  • 交付门面__init__ 门面（__all__）→ README 六节 → 5 分钟陌生人测试 —— 把「我能跑」变成「别人也能跑」；接口稳定、文档可信、接管成本趋零。

第五条「学习方法论」（踩坑索引 / 发现式调试 / 遗忘曲线自测 / 陌生人测试）是横切所有主线的元技能——它决定前四条链的牢固程度。

PART 02

分域知识点清单 按域归档，标注掌握深度

🧰 环境与版本控制

  • venv 本质：带解释器的文件夹，激活 = PATH 前插
  • git 三区模型：add / commit / push 的搬运路径
  • SSH 挑战-应答：私钥永不上传，密码不上网
  • non-fast-forward 三步法：fetch → log 区间 → rebase
  • rebase 改写历史：hash 由「内容+父提交」决定
  • where.exe 排查命令归属；VS Code 环境快照
  • git mv + rename 检测（83%）+ log --follow

🐍 Python 工程化

  • 类型注解三价值：错误前移 / 注解即文档 / 敢重构
  • list[int]、str | None 等核心语法
  • 装饰器 vs 继承：@ = 加工，括号 = 是什么
  • dunder 与 __main__ 入口；模块顶层只放声明
  • pyproject（意图）vs uv.lock（事实）；sync 多退少补
  • 运行时依赖 vs dev 依赖组（PEP 735）
  • 包门面：相对导入 / __all__ / __version__

🛡️ 质量防线

  • dataclass vs pydantic：储物柜 vs 安检门
  • model_validate 收 dict；必填 = 无默认值字段
  • 错误类型码阅读：missing / int_parsing / arg-type
  • pytest 四武器：assert / fixture / parametrize / raises+match
  • 表驱动约束矩阵；边界值必测（0/150 开关点）
  • 覆盖率：体检指标非 KPI；pragma 显式管理缺口
  • 三阶段失败形态：collection / setup / FAILED

📡 边界与观测（W3 开篇）

  • print 四宗罪：不可关 / 无级别 / 无上下文 / 无法收集
  • logging 五级别 = 过滤旋钮；getLogger(__name__) 署名
  • 结构化日志：一条记录而非一句话，可检索可串联
  • pydantic-settings：.env + env_prefix + 密钥分离
  • .env 入 gitignore；配置类型校验白送

📚 学习方法论（横切元技能）

  • 验收标准驱动：每个学习日先定「做到什么程度算完成」
  • 踩坑索引：报错 → 原因 → 解法 三段式沉淀，16+ 条可检索
  • 发现式调试：先跑真实失败、读原文，再编码断言——不凭记忆猜
  • 遗忘曲线自测：3 天节点盲测；本轮实测「动手型 75% vs 概念型 17%」
  • 陌生人测试：文档的唯一真实性检验
PART 03

真实工作场景映射 这些知识在入职后的日常里长什么样

工作情境动用的知识具体做法带来的价值
接手同事的项目src layout · pyproject · uv syncclone → uv sync 一条命令起环境 → 按 README 跑通上手成本从半天踩坑降到 5 分钟；环境与你同事完全一致
修改老功能pytest 安全网 · git 分支先跑测试存基线 → 开分支修改 → 全绿才合并；改坏了测试立刻红重构敢下手；「改 A 坏 B」当场暴露而非上线后爆炸
开发新接口dataclass / pydantic 选型 · 类型注解外部请求体用 pydantic 模型（自动校验+报 422），内部传递用 dataclass；mypy 全程把关脏数据在边界被拦，错误在写代码时暴露而非半夜在线上
排查线上问题结构化日志 · 级别旋钮关键动作记 logger.info(event=..., user_id=...)；出事时按字段检索、按级别过滤噪音分钟级定位（日志字段检索）vs 翻 print 大海碰运气
修一个 bug回归防线 · pytest.raises先写一个能复现 bug 的失败测试 → 修代码到绿 → 测试永久留下同一个 bug 在这个项目里永不复发
管理密钥与配置.env · pydantic-settings · gitignore密钥进 .env（不入库），代码只声明字段；dev/prod 用不同 .env 切换密钥零泄露风险；换环境不改一行代码
团队协作提交commit 范围前缀 · rebase · --followpush 被拒先 fetch 诊断；冲突用 rebase 保历史直线；改名用 git mv 保族谱历史可追溯、可审查；code review 时同事看得懂每一笔
向他人交付项目README 六节 · 包门面 · 陌生人测试按六节模板写文档 → 自己扮陌生人只按文档跑通接管成本趋零；你休假时团队不会瘫痪

共同规律：每条知识的价值都不是孤立的「会用命令」，而是把某类事故的发生时点从「线上/深夜」前移到「写代码的当下」——这就是工程素养的经济学。

PART 04

应用难点与改进方向 诚实的短板清单，按优先级排序

难点 1 · 概念型知识 4 天遗忘 83%。Day 006 的测试理念（三重身份/金字塔/值得测）自测只剩 17%——不是没学过，是学完没有复用场景。
改进：概念必须挂到实操钩子上。W3 后半写日志测试、接 CI 时强制复用；周日重测 Day 006 概念套件，及格线 80%。
难点 2 · 测试只覆盖纯函数。目前的 14 个测试全是无副作用函数（parse_age/activate）。真实工作里大量代码带 IO、网络、时间——这些还没测过。
改进：W3 起引入 fixture 进阶（临时文件、monkeypatch）；遇到带 IO 的函数时先问「怎么把它设计成可测的」。
难点 3 · 结构化日志只有观念没有形态。今天用 basicConfig 打出了 INFO:useradmin.models:...，但字段化输出（JSON/键值对）还没实操。
改进：D12 立即落地——formatter 输出键值对，为下周 request_id 链路铺路。
难点 4 · 质量防线未闭环。mypy 和 pytest 目前靠手动跑，没有强制力——忘跑就形同虚设。
改进：本周 D13–15 接入 pre-commit（提交时自动检查）+ GitHub Actions（push 时自动跑测试），让防线自动化。
难点 5 · 练习包太小，真实复杂度未遇到。useradmin 只有一个模块三个函数；依赖冲突、循环导入、性能问题都没现身。
改进：不焦虑——W4 数据管道周会引入真实数据规模，W8 FastAPI 会引入真实接口复杂度。能力在项目里长，不在练习里。
已确认的改进机制（保持）：① 踩坑索引持续沉淀（16 条）；② 每日验收标准先行；③ 阶段自测 + 遗忘曲线重测（W10/W18 工具栈重测待触发）；④ README 陌生人测试（待确认已执行）；⑤ 教学模式：讲解 → 自己动手 → 验证。
