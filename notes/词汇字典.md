## 一、环境与工具链

| 术语 | 中文释义 | 通俗解释 | 典型场景 |
| --- | --- | --- | --- |
| venv | 虚拟环境 | 自带独立 Python 解释器的文件夹，激活 = 把它的路径插到 PATH 最前面 | 每个项目一个 `.venv`，依赖互不污染 |
| PATH | 环境变量路径表 | 系统找命令的「地址簿」，按顺序查找，第一个命中生效 | 敲 `git` 报 command not found 时，先查 PATH |
| where.exe | 命令定位器 | 列出 PATH 里所有同名命令及其来源，识破「李鬼」 | 系统里疑似有多个 git/python 时排查 |
| 环境变量快照 | 进程启动时拍的环境副本 | VS Code 主进程启动时拍快照，新装软件要完全重启才生效 | 新装软件后终端找不到命令 |
| winget | Windows 包管理器 | 微软官方的「应用商店命令行版」 | `winget install Git.Git` 装 Git |
| uv | 新一代 Python 包管理器 | 速度极快的 pip/venv 替代品，一个工具管虚拟环境、依赖、锁定 | `uv venv` / `uv sync` / `uv add` |
| uv.lock | 依赖锁文件 | 把每个包的**精确版本+哈希**钉死的清单，保证人人环境一致 | 团队协作、CI 环境复现 |
| uv sync | 环境同步命令 | 让虚拟环境与锁文件**完全一致：多退少补** | clone 项目后一条命令起环境 |
| pyproject.toml | 项目声明文件 | Python 官方标准的项目「身份证」：名字、依赖范围、构建方式 | 一切现代 Python 项目的起点 |
| 依赖组 (dev) | 开发依赖分组 | 只在开发机用的工具（mypy/pytest）与运行时依赖分开声明 | `[dependency-groups] dev = [...]` |
| 可编辑安装 (-e) | 快捷方式式安装 | 把你的包以「指向源码」的方式装进 venv，改代码立即生效 | `uv sync` 默认对本项目可编辑安装 |
| src layout | 源码目录布局 | 代码放 `src/包名/`，测试 import 到的是**安装后的包** | 防「本机能跑、装上就坏」 |
| .gitignore | 版本库黑名单 | 声明哪些文件不进 git（venv、.env、缓存） | `.env`、`.venv/`、`__pycache__/` |
| gitignore 尾斜杠 | 匹配范围限定符 | 条目带尾斜杠（`.coverage/`）= **只匹配目录**；不带 = 文件与同名目录都匹配 | 忽略 `.coverage` 这类**文件**时不要写斜杠 |
| EOF 换行符 (end-of-file) | 文本文件末尾约定 | POSIX 惯例：文本文件以 `\n` 结束；缺失会被 end-of-file-fixer 钩子自动补上 | pyproject.toml/config.py 被钩子 Fixing |
| stash 回滚冲突 | pre-commit 保护机制 | 暂存区与工作区同时有修改时，钩子修复与 stash 恢复撞车 → 全部回滚待重来 | `commit` 前一次 `git add -A` 到位可避免 |
| .env | 本地环境配置文件 | 存密钥和本地配置，**永不入库** | 数据库密码、API Key |
| pre-commit | 提交钩子框架 | 用 YAML 声明钩子，在 `git commit` 瞬间自动运行检查，不合格阻止提交 | `.pre-commit-config.yaml` + `pre-commit install` |
| ruff | 极速 linter | 检查代码问题（未使用导入/风格违规），`--fix` 可自动修 | `ruff check src --fix` |
| black | 代码格式化器 | 只管排版、风格零配置零争论（唯一格式哲学） | `black src tests` 统一排版 |
| git hooks | git 事件钩子 | `.git/hooks/` 里的事件触发脚本，pre-commit = commit 前自动执行 | 新 clone 仓库需重新 `pre-commit install` |
| 修复型 Failed | 钩子自动修复语义 | 钩子报 Failed 但显示 files were modified = 已自动修好，重新暂存提交即可 | pre-commit 跑两遍才绿是正常循环 |
| YAML 冒号空格规则 | 配置格式语法 | `key: value` 冒号后必须空格，列表项里的映射同样遵守；缩进必须对齐 | pre-commit 配置三连坑 |
| 规则集 (select) | linter 启用范围 | ruff 默认集不含 E501 超长行，显式 `select=["E","F","I"]` 才启用 | `[tool.ruff.lint]` in pyproject |
| 工具协调 | 多工具配置对齐 | 多个工具管辖同一维度时配置必须一致，否则互相打架 | ruff 与 black 的 line-length 统一为 100 |

## 二、Git 与版本协作

| 术语 | 中文释义 | 通俗解释 | 典型场景 |
| --- | --- | --- | --- |
| 三区模型 | 工作区/暂存区/本地仓库/远端 | 代码的四站搬运线：add → commit → push | 理解每条 git 命令到底搬了什么 |
| commit | 提交（存档点） | 把暂存区内容固化成本地仓库的一个快照，附说明 | 范围前缀 commit：`w02d1: ...` |
| origin | 远端别名 | 远端仓库在本地的「代号」，可自定义 | `git push origin main` |
| upstream (-u) | 上游跟踪绑定 | 告诉本地分支「以后默认跟哪个远端分支走」 | 首次 push 后，`git push` 不用再写全名 |
| push / pull / fetch | 推送/拉取/取回 | push 上传提交；pull = fetch + 合并；fetch 只下载远端状态不动本地 | push 被拒时先 fetch 诊断 |
| non-fast-forward | 非快进拒绝 | 远端有你没有的提交时，git 拒绝 push（防覆盖保护） | 两人同改一分支后 push |
| 分叉 (diverged) | 历史分岔 | 本地和远端各自长出了对方没有的提交 | fetch 后 `git log main..origin/main` 查看 |
| rebase | 变基 | 把本地提交「摘下来」接到远端最新之上，历史保持直线 | `git pull --rebase` 修 non-fast-forward |
| fast-forward | 快进 | 远端指针直接前移到你的提交，无分叉 | rebase 成功后的正常 push |
| git mv | 受控搬移 | 用 git 记录「改名/移动」，提交时自动识别 rename | `git mv models.py src/useradmin/` |
| rename 检测 | 改名识别 | git 按内容相似度判断「这是改名不是删除+新建」 | 提交输出里的 `rename ... (83%)` |
| `--follow` | 穿越改名追历史 | 让 `git log` 穿过改名节点，显示完整族谱 | `git log --follow src/.../models.py` |
| SSH 密钥 | 免密登录钥匙对 | 私钥（家门钥匙，永不上传）+ 公钥（锁，随便贴） | GitHub 免密码 push |
| 挑战-应答 | 认证机制 | 服务端用公钥出题，本地私钥作答，密码全程不上网 | `ssh -T git@github.com` 成功 |
| known_hosts | 主机名册 | 首次连接的服务器指纹记录，防中间人 | 首次 push 问 yes/no |
| A..B 区间 | 提交范围语法 | 「B 可达而 A 不可达」的提交集合 | `git log main..origin/main` 看远端多了什么 |
| LF / CRLF | 换行符差异 | Linux 用 LF，Windows 用 CRLF，git 自动转换时会警告 | `warning: LF will be replaced by CRLF`（无害） |

## 三、Python 语言与工程

| 术语 | 中文释义 | 通俗解释 | 典型场景 |
| --- | --- | --- | --- |
| 类型注解 (type hints) | 类型标注 | 给变量/函数参数声明「应该是什么类型」，本身不影响运行 | `def parse_age(raw: str \| None) -> int \| None` |
| 静态检查 (mypy) | 不运行代码的体检 | 读代码就能发现类型矛盾，错误在写代码时暴露 | `mypy src` 全绿才提交 |
| dataclass | 数据类 | 标准库装饰器，按字段注解自动生成构造器，**无运行时校验** | 内部可信数据传递 |
| pydantic / BaseModel | 数据校验库 | 构造时**强制校验**类型与约束，坏数据当场抛错 | API 请求体、外部 JSON |
| model_validate | 解析式构造 | pydantic 的「安检入口」：收一个原始 dict，校验+转换+构造 | 解析外部不可信数据 |
| Field | 字段约束声明 | 给字段加运行时规则（范围/长度等） | `age: int = Field(ge=0, le=150)` |
| ValidationError | 校验失败异常 | pydantic 拦截坏数据时抛出，一次报出**所有**错误 | 拿错误类型码定位问题 |
| 错误类型码 | 校验错误分类标签 | `[type=missing]` 缺字段 / `[type=int_parsing]` 转不动 / `[type=arg-type]` | 按码查官方文档 |
| 装饰器 (decorator) | 类/函数加工器 | `@xxx` 把下面的东西交给函数加工后放回，等价 `X = xxx(X)` | `@dataclass`、未来的 `@app.get()` |
| dunder | 双下划线魔法名 | `__name__`、`__init__` 这类 `__xx__` 命名的内置机制 | `if __name__ == "__main__":` |
| 模块顶层副作用 | import 时执行的代码 | 写在模块最外层、import 就会跑的语句（print/IO）——工程大忌 | 顶层只放类/函数/常量声明 |
| `__main__` 入口 | 直接运行开关 | 直接运行本文件才执行、被 import 时跳过 | 脚本与可复用模块的分界 |
| 包门面 (__init__) | 对外统一入口 | 在 `__init__.py` 里集中导出，使用者不必知道内部结构 | `from useradmin import InternalUser` |
| `__all__` | 导出白名单 | 声明 `import *` 时允许导出什么 | 门面只展示该展示的 |
| 相对导入 (`.models`) | 包内互引用 | `.` = 当前包，包内模块互相引用的标准写法 | 门面文件里 `from .models import ...` |
| `# type: ignore[码]` | 类型检查逃生舱 | 显式压掉该行指定类型的 mypy 报错，**必须配注释说明原因** | 故意类型不对的演示/兼容代码 |
| `# pragma: no cover` | 覆盖率排除标记 | 让该行及代码块退出覆盖率统计 | `__main__` 演示块 |

## 四、测试与质量

| 术语 | 中文释义 | 通俗解释 | 典型场景 |
| --- | --- | --- | --- |
| pytest | 主流测试框架 | 按 `test_*.py` / `test_*` 命名自动发现测试 | `uv run pytest -v` |
| 断言 (assert) | 结果验证语句 | 声明「这里应该等于什么」，pytest 失败时展示左右值 | `assert parse_age("30") == 30` |
| fixture | 测试前置准备 | 可复用的「现成对象」构造器，测试当参数收 | `sample_user` 用户对象 |
| parametrize | 参数化 | 一组数据跑同一个测试函数，消灭复制粘贴 | 约束矩阵 7 行场景 |
| 用例 ID | 参数化用例名 | 报告里 `[25-25]` 这类参数拼接标识，失败直接点名 | 定位哪组数据挂了 |
| pytest.raises | 异常断言 | 声明「块内必须抛出某异常」，配 match 还能验内容 | `raises(ValidationError, match="Field required")` |
| 表驱动测试 / 约束矩阵 | 数据驱动测试 | 「输入+预期」抽成表格，函数只是执行器，加场景=加一行 | RegisterRequest 七行矩阵 |
| 覆盖率 (coverage) | 测试执行比例 | 被测试跑到的语句占比；体检指标非 KPI | `pytest --cov=useradmin` |
| 回归测试 | 防复发测试 | 修过的 bug 写测试钉住，永不复发 | 每修一个 bug 补一个测试 |
| 测试金字塔 | 单元多、集成少的分层 | 单元测试快而多（下层），集成测试慢而少（上层） | 规划测试组合 |

## 五、日志与配置

| 术语 | 中文释义 | 通俗解释 | 典型场景 |
| --- | --- | --- | --- |
| print 反模式 | 工程禁止项 | print 调试四宗罪：不可关/无级别/无上下文/无法收集 | 面试与 code review 高频考点 |
| 日志级别 | 过滤旋钮 | DEBUG<INFO<WARNING<ERROR<CRITICAL，按环境开关信息量 | 开发开 DEBUG，生产只留 INFO+ |
| getLogger(__name__) | 模块署名 logger | 日志自动带上「来自哪个模块」 | `logger = logging.getLogger(__name__)` |
| 结构化日志 | 字段化记录 | 每条日志是一条记录（key=value）而非一句话，可检索/聚合/串联 | `event=user_activated user_id=1` |
| structlog | 结构化增强库 | 在 logging 之上输出键值对/JSON 格式（知道即可） | W3 后半与生产环境 |
| pydantic-settings | 配置管理库 | 从环境变量/.env 读配置，**顺带类型校验**（pydantic 亲儿子） | `Settings` 类 + `.env` |
| env_prefix | 环境变量前缀 | 给配置变量加统一前缀防撞名 | `USERADMIN_LOG_LEVEL` |
| 密钥分离 | 配置安全铁律 | 密钥只存 .env（不入库），代码里只有字段声明 | `.env` 在 .gitignore 里 |
| 日志格式占位符 | 字段化输出模板 | `%(asctime)s %(levelname)s %(name)s %(message)s` 四件套，让日志的时间/级别/模块/消息各归其位 | `logging.basicConfig(format=...)` |
| setup_logging | 日志配置单点化 | 把日志初始化收敛成一个函数，所有入口统一调用，保证全程序格式唯一 | `logconfig.py` 中的 `setup_logging()` |
| fail-fast | 快速失败 | 配置缺失/非法时在**启动瞬间**报错退出，而不是跑到一半在业务逻辑里崩 | Settings 无默认值字段缺失即抛 ValidationError |
| 环境变量优先级 | 配置取值顺序链 | **真实环境变量 > .env 文件 > 代码默认值**；生产靠注入环境变量切换行为，无需 .env | `USERADMIN_LOG_LEVEL=ERROR uv run ...` 压过 .env |

## 六、学习方法论

| 术语 | 中文释义 | 通俗解释 | 典型场景 |
| --- | --- | --- | --- |
| 验收标准驱动 | 先定完成线 | 每天先明确「做到什么程度算完成」再开始学 | 每日计划的目标字段 |
| 踩坑索引 | 错误经验库 | 报错→原因→解法 三段式沉淀，可检索 | 学习笔记顶部总索引（16+ 条） |
| 发现式调试 | 先观察再断言 | 先跑真实失败、读报错原文，再编码断言/修复 | pytest match 片段的来源 |
| 遗忘曲线自测 | 3 天节点盲测 | 学完 3 天做不翻书自测，暴露真实记忆状态 | 每日笔记的自测问题 |
| 检索式学习 | 用力回忆 | 主动回想比重读有效数倍——回忆越费力，巩固越深 | 自测答不出的题=复习靶点 |
| 陌生人测试 | 文档真实性检验 | 新开终端只按 README 操作一遍 | 交付前最后闸门 |
| 保留率分层 | 遗忘规律 | 动手复用型知识保留 ~75%，纯概念型 4 天只剩 ~17% | 决定「概念必须挂实操钩子」 |
| 静默失败 | exit 0 但零输出 | 最阴险的失败形态：命令「成功」了但什么都没发生 | 诊断五步：echo $? → pwd → echo $变量 → grep 代码 → probe 探测器 |
| probe 探测器 | 最小独立验证脚本 | 用一行独立代码测「管线本身通不通」，把问题与业务代码隔离 | `python -c "import logging; logging.basicConfig(...); ...info('probe')"` |
| CWD 相对路径铁律 | 相对路径原点规则 | 不以 / 开头的路径全部以**当前所在目录**为原点解析；开工先 `pwd` | git 路径 / mypy src / .env 查找——已三次现身 |

## 七、知识点必要性图谱

> 每行回答三个问题：**实际中干什么用 / 不学它什么问题会发生 / 和谁关联**。

| 知识点 | 实际应用中的作用 | 解决什么问题 | 与其他知识点的关联 |
| --- | --- | --- | --- |
| 虚拟环境与依赖管理 | 任何 Python 项目的第一步 | 「在我机器上是好的」——环境不一致导致的幽灵 bug | 是 src layout、uv sync、CI 的地基；隔离思想通向 Docker |
| Git 三区与远端协作 | 代码的保存、追溯、团队同步 | 改坏无法回退、多人协作互相覆盖、历史不可查 | push 被拒要用 rebase；提交历史配合 --follow 追溯；CI 监控的就是 push |
| SSH 认证 | 与 GitHub/服务器的免密安全通道 | 密码明文上网、账号被盗用 | 是 git 远端操作的前提；「公私钥分工」思想在部署服务器时复用 |
| 类型注解 + mypy | 让错误在写代码时暴露 | 运行时才炸的类型 bug；读不懂的函数签名 | pydantic 的字段就是注解；mypy 检查的范围由 src layout 决定；type: ignore 是它的逃生舱 |
| dataclass vs pydantic | 数据的「内政」与「边检」分工 | 脏数据穿透到系统内部；内外数据混用一团糟 | pydantic 依赖类型注解；model_validate 是 FastAPI 请求处理的原型；测试矩阵验证的就是这些约束 |
| 装饰器 | 不改原代码给类/函数加能力 | 重复样板代码；功能与业务耦合 | @dataclass 靠字段注解生成构造器；FastAPI 路由全靠装饰器 |
| src layout 与包结构 | 让项目「装得起来、测得准」 | 本机能跑、装上就坏；import 路径混乱 | 决定 mypy/pytest 的检查范围；是 uv sync 可编辑安装的前提；Docker COPY 的对象 |
| 依赖锁定与 dev 组 | 环境可复现 + 工具不污染生产 | 三台机器三个环境；开发工具被打进生产镜像 | pyproject 声明意图、lock 钉死事实；CI 按锁安装；与 Docker 镜像构建共用思想 |
| 包门面 (__init__/__all__) | 对外接口稳定、内部自由重构 | 使用者被内部实现绑架，一改就崩 | 是「隔离实现细节」思想的包级应用；README 快速开始示例基于门面 |
