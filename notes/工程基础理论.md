# 工程基础理论

> **定位**：本文件是学习体系的**理论层**——把日常实践中验证过的做法提炼为可脱离案例独立成立的原理。它回答的不是「怎么做」（见 `学习笔记.md`）和「叫什么」（见 `词汇字典.md`），而是「**为什么这样做是对的**」。
>
> **成书约定**：每条命题均标注验证来源（Day 编号的亲手实验）；理论随进度扩充——当前为第一卷，覆盖 Day 001–011（环境筑基 + Python 工程化 + W3 开篇）。

## 第一章 · 环境隔离理论

### 命题 1.1 —— 一致性先于正确性

> **一个无法复现的环境，其中的「正确」毫无意义。**

程序行为的正确性以环境为前提。同一份代码在不同依赖组合下表现不同，此时讨论对错没有意义。因此工程实践的第一原则是：**先把环境钉死，再谈代码**。

- 机制：依赖声明（pyproject.toml 表达**意图**——版本范围）与依赖锁定（uv.lock 记录**事实**——精确版本与哈希）分离；同步操作（uv sync）保证「环境 = 锁」的严格相等，执行哲学为**多退少补**。
- 实验依据：Day 005（uv sync 卸载未声明的 mypy）验证了黑户清退纪律；Day 006–007 的测试结果在锁定环境下稳定复现。

### 命题 1.2 —— 隔离层级决定故障半径

> **隔离做得越轻，出问题时波及的范围越大。**

隔离存在递进的层级谱系，每一层解决上一层解决不了的污染问题：

```
包级隔离（venv：依赖互不污染）
  → 项目级隔离（src layout：import 指向安装后的包，杜绝「本机能跑、装上就坏」）
    → 仓库级隔离（.gitignore：密钥与产物不入库）
      → 系统级隔离（Docker 容器：操作系统层一致，后续卷）
```

- 实验依据：Day 005（src layout 验证「测试对象 = 发布对象」）；Day 012（.env 入 gitignore 验证密钥隔离）。

### 命题 1.3 —— 相对路径以进程工作目录为原点

> 一切不以绝对路径开头的路径解析，均以当前工作目录（CWD）为原点。

此规则适用于 git 参数、mypy 检查目标、.env 查找等几乎所有工具链行为。由此推论：**开工前的第一个反射是确认 CWD（pwd）**。

- 实验依据：三次独立踩坑（Day 005 git 路径、Day 006 mypy src、Day 012 .env 查找）。

## 第二章 · 版本控制理论

### 命题 2.1 —— 提交是不可变的事实记录

> 提交的哈希由「内容 + 父提交」共同决定，因此历史无法被悄悄篡改——rebase 是显式地重写历史，而非修改历史。

由此推论：提交后的哈希变化必然意味着父链变化；`git log --follow` 能穿越改名，因为内容相似度检测独立于路径。

- 实验依据：Day 005（笔记提交 rebase 后 hash 由 1b0de55 → 1384559）；Day 008（rename 检测 83% 相似度）。

### 命题 2.2 —— 拒绝是保护，不是阻碍

> 版本控制系统的所有「拒绝」行为（non-fast-forward、冲突提示）都在防止不可逆的信息丢失。

诊断路径因此标准化：**先 fetch 观察差异（main..origin/main），再选择合并策略**，永远不要在未知状态下强制操作。

- 实验依据：Day 005（non-fast-forward 三步法完整走通）。

### 命题 2.3 —— 认证的本质是证明持有秘密，而非传输秘密

SSH 挑战-应答模型中，私钥永不离开本机：服务端用公钥出题、客户端用私钥应答。推论：**凡需要认证的场景，优先设计「证明持有」而非「传输凭据」**的机制。

- 实验依据：Day 001（GitHub SSH 全流程）。

## 第三章 · 类型系统与静态分析

### 命题 3.1 —— 错误的发现时点决定修复成本

> 同一个类型错误，在 IDE 里发现成本约等于零；在代码评审中发现成本是一次往返沟通；在线上发现成本是故障与信任。

静态类型检查（mypy）的本质是**把错误发现时点尽可能前移**。这是全部质量防线的经济学基础，也是后续 pytest、CI 共同的底层逻辑。

### 命题 3.2 —— 注解是可被机器消费的元数据

> 类型注解不只是给人看的注释——运行时框架可以读取注解并据此生成行为。

证据：dataclass 按字段注解自动生成 `__init__`/`__repr__`；pydantic 按注解决定校验规则与解析行为。推论：**注解的准确性同时影响静态检查与运行时行为**，它是连接静态世界与动态世界的桥梁。

### 命题 3.3 —— 静态检查是契约检查，不是万能证明

mypy 能验证「代码内部类型自洽」，不能验证「运行时输入符合预期」——后者属于动态校验（pydantic）与测试（pytest）的管辖。三层各司其职：**静态查自洽、动态查输入、测试查行为**。逃生舱（type: ignore）的存在即承认此边界——使用时必须附注理由，使例外显式化。

### 命题 3.4 —— 模块顶层只允许声明

> 模块被 import 时，顶层语句全部执行。因此顶层只应放声明（类/函数/常量），一切副作用（IO、print、状态修改）必须封装进函数或 `__main__` 入口。

违反的代价：任何导入方都会被动执行副作用，且难以定位（输出出现在 import 者的上下文中）。

- 实验依据：Day 012（模块顶层残留 print 导致 pytest 收集日志污染，两处谜案同源）。

## 第四章 · 数据校验的边界理论

### 命题 4.1 —— 信任边界决定校验策略

> 数据的可信度由其来源决定，校验强度应与来源的可信度反相关。

```
系统内部产生的数据（可信）—— dataclass：结构声明，无运行时校验
系统边界进入的数据（不可信）—— pydantic：构造期强制校验，坏数据当场拒绝
```

两种构造入口的分工由此确定：构造函数服务静态契约（代码内手写数据），`model_validate` 服务动态解析（外部原始 dict）。

### 命题 4.2 —— 必要性用类型系统表达

> 无默认值的字段即必填字段——「必须提供什么」不需要文档和口头约定，直接编码进类型。

缺失时抛出 `[type=missing]`，值非法时抛出 `[type=int_parsing]`——错误类型码使失败原因可分类、可检索、可编程处理。

### 命题 4.3 —— fail-fast：配置错误死于启动瞬间

> 缺失或非法的配置应在系统启动的第一秒触发崩溃，而非在业务运行中被延迟引爆。

- 机制：Settings 无默认值字段 → 启动即 ValidationError。
- 价值对比：启动期崩溃的修复成本是「读一行报错」；运行期崩溃的修复成本是「深夜排障 + 信任损失」。
- 实验依据：Day 012（移除 .env 后启动即报错）。

## 第五章 · 测试理论

### 命题 5.1 —— 测试是代码正确性的可执行证明

> 测试的三重身份：重构的安全网（改动后全绿才敢提交）、可执行的文档（示例即证据）、回归的防线（修复过的 bug 永不复发）。

没有测试的代码库，其每次修改都是赌博——这是「不敢重构」现象的根因。

### 命题 5.2 —— 测试的价值密度取决于分支覆盖，而非用例数量

> 一组重复覆盖同一分支的用例，价值低于覆盖三个不同分支的用例。

参数化（parametrize）的正确用法是**分支枚举**：正常路径、空值、非法值至少各一。边界值（0/150 这类约束开关点）必测，因为比较运算的 off-by-one 错误几乎只发生在边界。

- 实验依据：Day 006（四组同分支用例被纠偏）；Day 007（七行约束矩阵）。

### 命令 5.3 —— 覆盖率是盲区探测器，不是成就指标

> 覆盖率回答「哪些代码没被测试执行过」，不回答「测试写得好不好」。

使用纪律：缺口要么补测试、要么显式排除（pragma）并附理由。追求表面 100% 而无断言质量的覆盖，是指标的异化。

### 命题 5.4 —— 可测试性是设计属性

> 纯函数（输入输出明确、无副作用）天然可测；混入 IO、全局状态修改的函数不可测。测试困难时应首先怀疑设计，而非测试技术。

推论：**测试驱动的不只是验证，还有更好的代码结构**。

## 第六章 · 质量防线自动化

### 命题 6.1 —— 一致性高于个人偏好

> 代码风格的唯一可辩护立场是「全仓库一致」，而人是最不可靠的一致性来源。风格判断交给机器（ruff/black），人类评审只保留给逻辑。

### 命题 6.2 —— 防线的强度取决于触发时机与强制力

```
本地手动跑（靠自觉）→ 提交钩子（pre-commit，强制）→ CI（push 后强制，全量）
```

三道防线的触发时机逐级后移、强制力逐级增强、覆盖环境逐级真实。**手动检查不构成防线**——它依赖记忆，而记忆不可靠。

- 实验依据：Day 013（pre-commit 门卫拦截循环：埋雷 → 拦截 → 自动修复 → 放行）。

### 命题 6.3 —— 自动修复型反馈是最高效的反馈形态

> 修复型 Failed（钩子已自动修好文件并要求重新暂存）优于报错型反馈：前者把「发现问题」与「解决问题」合并为一步。

「跑两遍才绿」是自动修复循环的正常形态：第一遍修复，第二遍确认。

## 第七章 · 可观测性与配置理论

### 命题 7.1 —— 生产代码的输出必须是机器可处理的

> print 调试的四宗罪（不可关闭、无级别、无上下文、无法收集）本质上都是同一缺陷：**输出是给人看的句子，不是给系统处理的记录**。

结构化日志（字段化记录）使日志具备可检索、可聚合、可串联的属性——这是从「能跑」到「可运维」的分界。

### 命题 7.2 —— 日志级别是信息流量的控制阀

> 五级别（DEBUG<INFO<WARNING<ERROR<CRITICAL）的本质是按环境调节信噪比：开发期最大化信息，生产期最小化噪音。

- 实验依据：Day 012（.env 切换 DEBUG/WARNING，INFO 日志随之生灭）。

### 命题 7.3 —— 配置的取值优先级必须显式且稳定

> 真实环境变量 > 环境文件（.env）> 代码默认值。

此链路使「同一份代码、不同环境、零修改」成为可能：本地用 .env，生产由部署平台注入环境变量。配套纪律：密钥只存于不入库的文件，声明与取值分离。

## 第八章 · 工程元原则（横切各章）

1. **显式优于隐式**——依赖必须声明（黑户清退）、例外必须注解（type: ignore 带理由）、排除必须标记（pragma 带说明）。
2. **副作用必须封装**——模块顶层只放声明（命题 3.4）。
3. **一切路径以 CWD 为原点**——操作前确认所在目录（命题 1.3）。
4. **预期必须来自系统真实行为**——测试断言记录现状，改变现状去改系统而非改测试（Day 007 空字符串案例）。
5. **修复型反馈优于报错型反馈**——能自动修的就不要只报错（命题 6.3）。
6. **验证优先于假设**——静默 ≠ 成功，先查退出码与证据（Day 012 诊断五步）。
