### 二、核心知识点

#### 1. 虚拟环境（venv）的本质

**一句话**：venv 就是一个自带独立 Python 解释器（副本）的文件夹，"激活"只是把它的路径插到 PATH 最前面。

- 创建：`python -m venv .venv` → 在当前目录生成 `.venv/` 文件夹
- 激活的本质：把 `.venv\Scripts` 插到 PATH 前端，之后敲 `python` 优先找到它
- 激活后命令行前面出现 `(.venv)` 前缀 = 提示"你现在用的是谁家的 Python"
- 依赖隔离：每个项目一个 `.venv`，互不污染；`pip list` 可以验证里面只有干净的几个包
- `.venv` 必须进 `.gitignore`（几百 MB 且跨机器不可复用，`requirements.txt` 才是要提交的）

#### 2. Git 安装与命令排查

- 安装：`winget install --id Git.Git`（Windows 官方包管理器）
- **排查命令归属**：`where.exe git` 列出 PATH 中所有同名命令，按顺序第一个生效
- 今天踩的坑：环境体检时检测到的 git 2.55.0 其实是 WorkBuddy 自带的便携版（在 `/mingw64/bin/`），系统里根本没装——`where.exe` 是识破这类"李鬼"的工具

#### 3. VS Code 终端与环境快照

- VS Code 的**主进程**在启动时对环境变量拍了一张"快照"，之后新开的终端都继承这张旧快照
- 所以**刚装完新软件，新开终端没用，必须完全退出 VS Code 再重开**（不是关窗口，是退出进程）
- 终端下拉菜单（`+` 旁边的 ∨）里可以选 Git Bash / PowerShell

#### 4. SSH 密钥认证（挑战-应答）

- 生成：`ssh-keygen -t ed25519 -C "1114259706@qq.com"`
- 两个文件的分工：
  - `~/.ssh/id_ed25519` = **私钥**（绝对不外传，等同于家门钥匙）
  - `~/.ssh/id_ed25519.pub` = **公钥**（随便贴，等同于锁）
- 认证流程：GitHub 用你登记的公钥出一道题（挑战）→ 本地私钥解出答案（应答）→ **密码全程不上网**
- 首次连接会提示 host key 确认（yes）→ 写入 `~/.ssh/known_hosts`，以后不再问
- 指纹核对法：`ssh-keygen -lf ~/.ssh/id_ed25519.pub` 可以在不暴露公钥内容的情况下核对身份

#### 5. Git 三区模型（本日最重要的心智模型）

```
工作区 ──git add──> 暂存区 ──git commit──> 本地仓库 ──git push──> 远端(origin)
      <──git checkout--    <----git reset----    <---git pull----
```

- `origin` 只是远端仓库的**别名**（`git remote add origin git@github.com:SCIICO/ai-learning.git` 时起的）
- `git push -u origin main` 的 `-u` = 绑定 upstream 跟踪关系，此后只需 `git push` / `git pull`
- 验证绑定：`git branch -vv`，输出里 main 后面的 `[origin/main]` 就是绑定标志
- push 输出逐行读法：
  - `Enumerating objects: 9` → 本地清点要上传的对象
  - `* [new branch] main -> main` → 远端**新建**了 main 分支（以后再 push 就没有 `new` 字样）
  - `Branch 'main' set up to track 'origin/main'` → `-u` 生效的证据

#### 6. 建仓库的一个隐藏坑

在 GitHub 网页建仓库时**不要勾选 "Add a README file"**：勾了会在远端产生一个初始提交，和本地 `git init` 后的历史对不上，push 会被拒（分叉）。本地已经有内容时，远端保持全空最干净。

### 三、今日亲手敲过的命令（速查）

```bash
# 虚拟环境
python -m venv .venv
source .venv/Scripts/activate      # Git Bash 激活
deactivate                          # 退出

# Git 安装与排查
winget install --id Git.Git
where.exe git                       # 查命令到底来自哪

# SSH 密钥
ssh-keygen -t ed25519 -C "1114259706@qq.com"
cat ~/.ssh/id_ed25519.pub | clip    # 复制公钥到剪贴板（避免折行）
ssh-keygen -lf ~/.ssh/id_ed25519.pub  # 核对指纹
ssh -T git@github.com               # 测试 GitHub 连通

# Git 三区全流程
git init
git status
git add .
git commit -m "README: init ai-learning repo"
git remote add origin git@github.com:SCIICO/ai-learning.git
git push -u origin main
git branch -vv                      # 验证 [origin/main] 绑定
git log --oneline

# push 被拒（non-fast-forward）时的诊断与修复
git fetch origin                     # 只同步远端状态，不动工作区
git log --oneline main..origin/main  # 看远端多出了哪些提交
git pull --rebase origin main        # 把本地提交 rebase 到远端之上
git push
```

> **LF/CRLF warning 不是错误**：Linux 换行用 LF，Windows 用 CRLF，git 自动转换前会知会一声，可无视。
>
> **重要认知**：提交 hash 由「内容 + 父提交」共同决定。rebase 换掉父提交后，同一份笔记提交的 hash 会从 `1b0de55` 变成 `1384559`——rebase 本质是改写历史。

### 二、核心知识点

#### 1. 一次 `docker run` 背后的四步工作流

hello-world 的输出就是官方教材：

1. **client 联系 daemon** —— 你敲的 `docker` 命令只是遥控器，干活的是后台常驻引擎。所以改配置（如加速器）要重启的是 daemon
2. **daemon 拉镜像** —— 本地没有就从远端 registry 拉（`amd64` = CPU 架构）
3. **由镜像创建容器并运行** —— 类 → 实例
4. **输出流回终端** —— 容器内 stdout → daemon → client → 你的屏幕

#### 2. 镜像 vs 容器（本日最重要的心智模型）

| | 镜像 (image) | 容器 (container) |
| --- | --- | --- |
| 类比 | 类 class | 实例 object |
| 性质 | 只读模板，持久 | 运行实例，**跑完即弃** |
| 命令 | `docker images` | `docker ps`（运行中）/ `docker ps -a`（全部含已退出） |

`Exited (0)` 两个信息的读法：状态 = 已停止；`0` = 退出码，0 表示程序正常跑完退出（非崩溃）。

#### 3. `docker run -it python:3.12 bash` 逐段解剖

- `-i` interactive：保持标准输入打开（能敲键盘）
- `-t` tty：分配伪终端（有提示符、能退格）—— 与 `-i` 几乎总是连写成 `-it`
- `python:3.12`：镜像名:标签（官方 Python 3.12，~1.6GB）
- `bash`：容器启动后执行的程序，这里是 shell

### 二、核心知识点

#### 1. 类型注解的三重价值

① **错误前移**：mypy 不运行代码就能抓类型错误（静态检查）；② **注解即文档**：签名是最可靠的说明书；③ **重构敢下手**：工具能列出所有受影响调用点。关键认知：**注解本身不影响运行**（Python 默认不校验），校验靠 mypy 这类工具——所以叫「静态」。

#### 2. 必会语法（今日覆盖）

```python
scores: list[int] = [90, 85]        # 容器要写内部类型
nickname: str | None = None         # 可空（3.10+ 写法，旧写法 Optional[str]）
def find(uid: int) -> str | None: ...   # 参数类型 + 返回类型
```

#### 3. dataclass vs pydantic：安检门 vs 储物柜（本日核心）

| | `@dataclass`（标准库） | `pydantic.BaseModel` |
| --- | --- | --- |
| 校验时机 | **无运行时校验**，照单全收 | **构造时强制校验**，坏数据当场抛 ValidationError |
| 典型输入 | 可信数据（自己代码内部传递） | **不可信数据**（API 请求体、JSON、配置、LLM 输出） |
| 额外能力 | 纯结构 + 方法 | 自动解析（"25" → int）、嵌套模型、序列化 |

**决策口诀：数据从哪来？内部可信 → dataclass；外部进来 → pydantic。**

**亲手采集的证据链**（破坏实验）：

- `RegisterRequest(age="abc")` → `ValidationError`，且一次报出**所有**错误（`[type=missing]` 缺字段 / `[type=int_parsing]` 解析失败），方括号错误码可直接搜官方文档
- `InternalUser(id="oops", username=123)` → 照单全收，类型形同虚设
- 规则：**没默认值的字段 = 必填字段**（少传一个就报 `[type=missing]`）

#### 4. 装饰器 vs 继承（今日最深的坑）

`@dataclass` 是**函数（装饰器）**，不是类，不能被继承。`@` 是语法糖，等价于 `X = dataclass(X)`——把类交给函数加工后拿回增强版。dataclass 会**读类里的字段注解**来自动生成 `__init__`/`__repr__`——注解在这里是被机器消费的代码。口诀：**继承（括号里）=「我是一种什么」；装饰器（头顶 @）=「帮我加工一下」**。

#### 5. `__main__` 入口、dunder、与「两份代码」

- `if __name__ == "__main__":` = 直接运行本文件才执行、被 import 时不执行——区分「脚本」与「可复用模块」的标准写法
- `__xxx__` 双下划线包裹 = **dunder**（double underscore），Python 用它命名内置魔法名（`__name__`、`__init__`）
- **编辑器里的代码 ≠ 磁盘上的代码**：mypy/终端只读磁盘文件，改完必须 `Ctrl+S`（今天的第 3 号坑的隐藏半场）

#### 2. pyproject.toml 与 uv.lock 的分工

- `pyproject.toml`：声明**意图**——包叫什么、依赖谁的什么版本范围（`pydantic>=2.7`）

- **开发工具**（`[dependency-groups] dev`）：mypy/pytest/ruff——只存在于开发机

#### 4. 构造函数 vs model_validate（边界的两种姿势）

```python

RegisterRequest.model_validate({"username": ..., "age": "25"})    # 解析原始 dict：运行时安检，pydantic 盯着
```

- 外部进来的数据（JSON 解析出来就是 dict）没有静态类型可言 → 用 `model_validate`
- `model_validate` 只收**一个 dict 位置参数**，不收 kwargs（今天用 mypy 的 call-arg 报错验证的）

#### 1. print 调试为什么是工程反模式

四宗罪：**无法关闭**（上线后还在刷）、**无级别**（致命错误和调试信息一个样）、**无上下文**（谁/何时/哪个请求）、**无法收集**（日志系统收不走）。logging 是这四个问题的官方答案。

#### 2. logging 最小知识集

```python
import logging

logger = logging.getLogger(__name__)   # logger 名 = 模块路径（useradmin.models），日志自带署名

logger.debug("...")     # 开发期细节，默认不显示
logger.info("...")      # 关键动作
logger.warning("...")   # 异常但可继续
logger.error("...")     # 出事了
```

五级别 DEBUG < INFO < WARNING < ERROR < CRITICAL；**级别 = 过滤旋钮**：开发开 DEBUG 全看，生产只留 INFO+。今天实验亲手验证：`.env` 从 DEBUG 改 WARNING，info 行立刻消失。

| 日志输出带结构化字段（时间/级别/模块/消息） | ✅ `2026-10-27 10:33:49,782 INFO useradmin.models user activated user_id=1` |

### 二、核心知识点

#### 1. 结构化日志字段（format 占位符四件套）

```python
logging.basicConfig(
    level=settings.log_level,
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
)
```

效果：`2026-10-27 10:33:49,782 INFO useradmin.models user activated user_id=1`——时间/级别/模块/消息**四个字段各归其位**，机器可按字段解析。对比 `print("用户激活成功")`：这就是「半结构化」（固定字段 + 消息体 key=value）。

#### 2. setup_logging 收敛模式

日志配置写成 `logconfig.py` 里的**单点函数** `setup_logging()`：任何入口（脚本、未来的 FastAPI、测试）都调它，保证全程序日志格式唯一。配置来源统一走 `settings`——**日志行为本身也受配置管理**。

#### 3. 环境变量优先级链（今日最重要的生产知识）

```
真实环境变量  >  .env 文件  >  代码默认值
```

- `USERADMIN_LOG_LEVEL=ERROR uv run python ...` → INFO 被压制（亲手验证）
- 生产含义：**部署平台注入环境变量即可切换行为，同一份代码零修改**——生产环境根本不需要 .env 文件

#### 4. fail-fast（快速失败）

Settings 加无默认值字段（`secret_key: str`）→ 配置缺失时 `Settings()` **在启动瞬间抛 ValidationError**。价值：配置问题崩在启动的第一秒，而不是跑到一半在深夜崩在业务逻辑里。

#### 5. 静默失败的诊断学（今日最大的收获）

「命令成功退出（exit 0）但毫无输出」是最阴险的失败形态。今天的五步诊断法：

```
① echo $?          → 确认是真成功还是假成功
② pwd              → 我在哪？相对路径全部以 CWD 为原点
③ echo $变量名      → shell 里有没有残留的环境变量在压制
④ grep -n 关键词    → 相关代码到底还在不在
⑤ 探测器            → 用最小独立脚本测管线本身（probe 法）
```

本次战果：①③⑤ 逐一排除后锁定「历史运行的遗留观察」——修复后重跑即通。**相对路径铁律第三次现身**（git 路径 / mypy src / .env 查找）：铁律升格——`pwd` 应成为排错的第一反射。

#### 1. 表驱动测试（约束矩阵方法论）

把「**输入 payload + 预期 match**」抽成表格数据，测试函数退化为纯执行器。加新场景 = 表里加一行，逻辑零改动。这就是数据驱动测试的雏形——W8 测 API、W18 做 RAG 评估回归都是同一模式。

```python
@pytest.mark.parametrize("payload,match", [
    ({"username": "sciico", "password": "123456", "age": 0}, None),      # 边界内
    ({"username": "sciico", "password": "123456", "age": 150}, None),    # 边界内
    ({"username": "sciico", "password": "123456", "age": -1}, "greater than or equal"),
    ({"username": "sciico", "password": "123456", "age": 151}, "less than or equal"),
    ({"username": "sciico", "password": "123456", "age": "abc"}, "valid integer"),
    ({"username": "sciico", "age": 25}, "password"),                     # 缺字段
    ({"username": "", "password": "123456", "age": 20}, None),           # 空串合法：记录现状
])
def test_register_matrix(payload: dict, match: str | None) -> None:
    if match is None:
        r = RegisterRequest.model_validate(payload)
        assert r.age == payload["age"]          # 没抛 ≠ 解析对：成功分支也要断言
    else:
        with pytest.raises(ValidationError, match=match):
            RegisterRequest.model_validate(payload)
```

#### 2. match 参数的两条规则 + 发现式用法

- match 是**字符串**（在异常信息里做正则搜索），异常类只放 raises 第一个参数——传类会 `TypeError: first argument must be string`
- match 是正则：`. * + ( ) [ ]` 等特殊字符要转义
- **发现式用法**：先跑一次真实失败 → 读报错原文 → 摘一段稳定短语填进 match。不凭记忆猜

#### 3. `# pragma: no cover`：显式管理缺口

`if __name__ == "__main__":  # pragma: no cover` 让该行及整个代码块退出统计。效果：models.py 的 Stmts 从 30 → 24，覆盖率 83% → 100%。**清醒认知**：覆盖率可以被「做」出来——所以排除必须配理由（注释就是理由），100% 只说明「缺口被显式管理」，不代表更安全。

#### 4. pytest 三阶段失败形态（今天集齐三种）

| 阶段 | 触发 | 报错长相 |
| --- | --- | --- |
| **collection ERROR** | 装饰器参数名与函数签名不匹配 | `ERROR collecting ... function uses no argument 'payload'`，`collected 0 items` |
| **setup ERROR** | 函数参数找不到供给方（fixture/parametrize 缺失） | `fixture 'payload' not found` |
| **FAILED** | 测试跑了，断言失败或异常没按预期抛 | `assert ...` / `DID NOT RAISE` |

流水线：收集 → setup → 运行。**阶段不同，修法完全不同**——先看报错属于哪一段。

#### 5. 参数名三处一致原则

parametrize 出问题先查三处：**装饰器字符串**（"payload,match"）、**函数签名**（def f(payload, match)）、**数据元组**（每行元素个数与顺序）。今天的三连坑全部出在这里。

#### 6. 两条测试设计纪律

- **边界值必测**：0 和 150 是 Field(ge=0, le=150) 的「开关点」——约束最容易在边界翻车
- **预期来自模型的真实行为，不是愿望**：age=1 合法、空字符串合法——测试是现状的文档；想改变现状去改模型（加约束），而不是让测试假装

### 二、核心知识点

#### 1. 测试的三重身份

① **安全网**——改代码后跑一遍，全绿就敢提交（没有它，代码从第二天起就不敢动）；② **可执行文档**——`test_parse_age("abc", None)` 比 README 的一句描述更可信；③ **回归防线**——修过的 bug 写个测试钉住，永远回不来。

#### 2. pytest 约定优于配置

文件名 `test_*.py`、函数名 `test_*` → 自动发现。断言用普通 `assert`：pytest 会**重写断言**，失败时把左右两侧的实际值摆出来——比老 unittest 的 `self.assertEqual` 信息量高一个量级。

#### 3. 四武器

| 武器 | 场景 | 要点 |
| --- | --- | --- |
| `assert` | 验证结果 | 失败时自动展示左右值 |
| `@pytest.fixture` | **前置准备**（构造对象/资源），多测试复用 | 测试函数把它当参数收；本次 `sample_user` |
| `@pytest.mark.parametrize` | 一组输入跑同一测试 | 用例价值在**覆盖分支**（正常/None/非法各一组），不在凑数量；报告里的 `[25-25]` 是用例 ID |
| `pytest.raises(Exc)` | **异常路径也是路径** | `with` 块内触发异常即通过 |

#### 4. 覆盖率与分层

- 覆盖率 = 被测试执行到的语句比例，**60–70% 起步达标**；100% ≠ 没 bug（「跑到了」≠「断言对了」），它是体检指标不是 KPI
- 本次报告读法：`models.py 30 stmts / 5 miss / 83% / Missing 39-47`——缺的正是 `__main__` 演示块（演示代码不进测试，这个缺口是合理判断的数字化体现）
- 分层金字塔：**单元测试**（隔离、快、多，占大头）在下，**集成测试**（组件协作、慢、少而精）在上

#### 5. 值得测 / 不值得测

- **值得**：有分支逻辑的（parse_age 三分支）、边界值、核心业务规则、修过的 bug
- **不值得**：第三方库内部（pydantic 自会测自己）、纯声明性代码（字段定义）、演示块

#### 6. 可测试性是设计出来的

`parse_age` 是理想测试对象：**纯函数、输入输出明确、无副作用**。反例：函数里混 `print`/`input`/改全局变量——想测都无从下手。好测试的前提是好设计。

#### 7. 两个语义区分（今天踩出来的）

- **空字符串 ≠ 缺失**：`password=""` 是「提供了但是空」（值校验范畴，可用 `Field(min_length=1)` 约束）；不传 password 才是 `[type=missing]`（结构校验）
- **测试名实必须相符**：一个名为 requires_all_fields 的测试实际靠 age=200 通过——三个月后回看会被彻底误导；测试名是承诺
