### 二、核心知识点

#### 1. 虚拟环境（venv）的本质

**一句话**：venv 就是一个自带独立 Python 解释器（副本）的文件夹，"激活"只是把它的路径插到 PATH 最前面。

- 创建：`python -m venv .venv` → 在当前目录生成 `.venv/` 文件夹
- 激活的本质：把 `.venv\Scripts` 插到 PATH 前端，之后敲 `python` 优先找到它
- 激活后命令行前面出现 `(.venv)` 前缀 = 提示"你现在用的是谁家的 Python"
- 依赖隔离：每个项目一个 `.venv`，互不污染；`pip list` 可以验证里面只有干净的几个包
- `.venv` 必须进 `.gitignore`（几百 MB 且跨机器不可复用，`requirements.txt` 才是要提交的）

#### 2. Git 安装与命令排查

- 安装：`winget install --id Git.Git`（Windows 官方包管理器）
- **排查命令归属**：`where.exe git` 列出 PATH 中所有同名命令，按顺序第一个生效
- 今天踩的坑：环境体检时检测到的 git 2.55.0 其实是 WorkBuddy 自带的便携版（在 `/mingw64/bin/`），系统里根本没装——`where.exe` 是识破这类"李鬼"的工具

#### 3. VS Code 终端与环境快照

- VS Code 的**主进程**在启动时对环境变量拍了一张"快照"，之后新开的终端都继承这张旧快照
- 所以**刚装完新软件，新开终端没用，必须完全退出 VS Code 再重开**（不是关窗口，是退出进程）
- 终端下拉菜单（`+` 旁边的 ∨）里可以选 Git Bash / PowerShell

#### 4. SSH 密钥认证（挑战-应答）

- 生成：`ssh-keygen -t ed25519 -C "1114259706@qq.com"`
- 两个文件的分工：
  - `~/.ssh/id_ed25519` = **私钥**（绝对不外传，等同于家门钥匙）
  - `~/.ssh/id_ed25519.pub` = **公钥**（随便贴，等同于锁）
- 认证流程：GitHub 用你登记的公钥出一道题（挑战）→ 本地私钥解出答案（应答）→ **密码全程不上网**
- 首次连接会提示 host key 确认（yes）→ 写入 `~/.ssh/known_hosts`，以后不再问
- 指纹核对法：`ssh-keygen -lf ~/.ssh/id_ed25519.pub` 可以在不暴露公钥内容的情况下核对身份

#### 5. Git 三区模型（本日最重要的心智模型）

```
工作区 ──git add──> 暂存区 ──git commit──> 本地仓库 ──git push──> 远端(origin)
      <──git checkout--    <----git reset----    <---git pull----
```

- `origin` 只是远端仓库的**别名**（`git remote add origin git@github.com:SCIICO/ai-learning.git` 时起的）
- `git push -u origin main` 的 `-u` = 绑定 upstream 跟踪关系，此后只需 `git push` / `git pull`
- 验证绑定：`git branch -vv`，输出里 main 后面的 `[origin/main]` 就是绑定标志
- push 输出逐行读法：
  - `Enumerating objects: 9` → 本地清点要上传的对象
  - `* [new branch] main -> main` → 远端**新建**了 main 分支（以后再 push 就没有 `new` 字样）
  - `Branch 'main' set up to track 'origin/main'` → `-u` 生效的证据

#### 6. 建仓库的一个隐藏坑

在 GitHub 网页建仓库时**不要勾选 "Add a README file"**：勾了会在远端产生一个初始提交，和本地 `git init` 后的历史对不上，push 会被拒（分叉）。本地已经有内容时，远端保持全空最干净。

### 三、今日亲手敲过的命令（速查）

```bash
# 虚拟环境
python -m venv .venv
source .venv/Scripts/activate      # Git Bash 激活
deactivate                          # 退出

# Git 安装与排查
winget install --id Git.Git
where.exe git                       # 查命令到底来自哪

# SSH 密钥
ssh-keygen -t ed25519 -C "1114259706@qq.com"
cat ~/.ssh/id_ed25519.pub | clip    # 复制公钥到剪贴板（避免折行）
ssh-keygen -lf ~/.ssh/id_ed25519.pub  # 核对指纹
ssh -T git@github.com               # 测试 GitHub 连通

# Git 三区全流程
git init
git status
git add .
git commit -m "README: init ai-learning repo"
git remote add origin git@github.com:SCIICO/ai-learning.git
git push -u origin main
git branch -vv                      # 验证 [origin/main] 绑定
git log --oneline

# push 被拒（non-fast-forward）时的诊断与修复
git fetch origin                     # 只同步远端状态，不动工作区
git log --oneline main..origin/main  # 看远端多出了哪些提交
git pull --rebase origin main        # 把本地提交 rebase 到远端之上
git push
```

> **LF/CRLF warning 不是错误**：Linux 换行用 LF，Windows 用 CRLF，git 自动转换前会知会一声，可无视。
>
> **重要认知**：提交 hash 由「内容 + 父提交」共同决定。rebase 换掉父提交后，同一份笔记提交的 hash 会从 `1b0de55` 变成 `1384559`——rebase 本质是改写历史。

### 二、核心知识点

#### 1. 一次 `docker run` 背后的四步工作流

hello-world 的输出就是官方教材：

1. **client 联系 daemon** —— 你敲的 `docker` 命令只是遥控器，干活的是后台常驻引擎。所以改配置（如加速器）要重启的是 daemon
2. **daemon 拉镜像** —— 本地没有就从远端 registry 拉（`amd64` = CPU 架构）
3. **由镜像创建容器并运行** —— 类 → 实例
4. **输出流回终端** —— 容器内 stdout → daemon → client → 你的屏幕

#### 2. 镜像 vs 容器（本日最重要的心智模型）

| | 镜像 (image) | 容器 (container) |
| --- | --- | --- |
| 类比 | 类 class | 实例 object |
| 性质 | 只读模板，持久 | 运行实例，**跑完即弃** |
| 命令 | `docker images` | `docker ps`（运行中）/ `docker ps -a`（全部含已退出） |

`Exited (0)` 两个信息的读法：状态 = 已停止；`0` = 退出码，0 表示程序正常跑完退出（非崩溃）。

#### 3. `docker run -it python:3.12 bash` 逐段解剖

- `-i` interactive：保持标准输入打开（能敲键盘）
- `-t` tty：分配伪终端（有提示符、能退格）—— 与 `-i` 几乎总是连写成 `-it`
- `python:3.12`：镜像名:标签（官方 Python 3.12，~1.6GB）
- `bash`：容器启动后执行的程序，这里是 shell

进入后提示符变为 `root@<随机ID>:/#` —— 你已身处容器内的 Linux。容器里的 `python` 是镜像自带的 3.12，**与 Windows 本机装什么版本完全无关**，这就是环境隔离的意义。

#### 4. 镜像加速器（registry mirror）

- 本质：Docker Hub 的「国内代购」，你向它要镜像，它替你回源取货缓存
- `registry-mirrors` 数组**按顺序尝试，不是并行**：第一个超时才试下一个 → 最稳的放最前
- URL 末尾**不能加 `/`**（Docker 读取后会自动归一化补上，显示带斜杠是正常的）
- 当前配置（2026-10 经查证可用）：`docker.1ms.run` / `docker.xuanyuan.me` / `docker.m.daocloud.io`
- 备用方案：阿里云「容器镜像服务」（免费）分配专属地址，长期最稳
- 配置入口：Docker Desktop → Settings → Docker Engine（JSON），实际落盘在 `C:\Users\<用户>\.docker\daemon.json`

### 四、踩坑记录（5 条，全自己动手解决）

| # | 现象 | 原因 | 解法 |

### 二、核心知识点

#### 1. 类型注解的三重价值

① **错误前移**：mypy 不运行代码就能抓类型错误（静态检查）；② **注解即文档**：签名是最可靠的说明书；③ **重构敢下手**：工具能列出所有受影响调用点。关键认知：**注解本身不影响运行**（Python 默认不校验），校验靠 mypy 这类工具——所以叫「静态」。

#### 2. 必会语法（今日覆盖）

```python
scores: list[int] = [90, 85]        # 容器要写内部类型
nickname: str | None = None         # 可空（3.10+ 写法，旧写法 Optional[str]）
def find(uid: int) -> str | None: ...   # 参数类型 + 返回类型
```

#### 3. dataclass vs pydantic：安检门 vs 储物柜（本日核心）

| | `@dataclass`（标准库） | `pydantic.BaseModel` |
| --- | --- | --- |
| 校验时机 | **无运行时校验**，照单全收 | **构造时强制校验**，坏数据当场抛 ValidationError |
| 典型输入 | 可信数据（自己代码内部传递） | **不可信数据**（API 请求体、JSON、配置、LLM 输出） |
| 额外能力 | 纯结构 + 方法 | 自动解析（"25" → int）、嵌套模型、序列化 |

**决策口诀：数据从哪来？内部可信 → dataclass；外部进来 → pydantic。**

**亲手采集的证据链**（破坏实验）：

- `RegisterRequest(age="abc")` → `ValidationError`，且一次报出**所有**错误（`[type=missing]` 缺字段 / `[type=int_parsing]` 解析失败），方括号错误码可直接搜官方文档
- `InternalUser(id="oops", username=123)` → 照单全收，类型形同虚设
- 规则：**没默认值的字段 = 必填字段**（少传一个就报 `[type=missing]`）

#### 4. 装饰器 vs 继承（今日最深的坑）

`@dataclass` 是**函数（装饰器）**，不是类，不能被继承。`@` 是语法糖，等价于 `X = dataclass(X)`——把类交给函数加工后拿回增强版。dataclass 会**读类里的字段注解**来自动生成 `__init__`/`__repr__`——注解在这里是被机器消费的代码。口诀：**继承（括号里）=「我是一种什么」；装饰器（头顶 @）=「帮我加工一下」**。

#### 5. `__main__` 入口、dunder、与「两份代码」

- `if __name__ == "__main__":` = 直接运行本文件才执行、被 import 时不执行——区分「脚本」与「可复用模块」的标准写法
- `__xxx__` 双下划线包裹 = **dunder**（double underscore），Python 用它命名内置魔法名（`__name__`、`__init__`）
- **编辑器里的代码 ≠ 磁盘上的代码**：mypy/终端只读磁盘文件，改完必须 `Ctrl+S`（今天的第 3 号坑的隐藏半场）
